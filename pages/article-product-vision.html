Product vision

A Simpler Way to Keep Track of What Matters

Alysha Pursley

The goals, users, screen plan, and technical direction I established for PunctuOwlity before implementation.

A lightweight tracker, not a full calendar

The goal I set for PunctuOwlity was to give people a quick and easy way to track upcoming events. I wanted them to create and manage personal reminders without unnecessary complexity: open the app, see what is coming up, and add or remove an event in seconds rather than minutes.

The product was deliberately smaller in scope than a comprehensive calendar. Its central jobs were account access, viewing events, and editing the details that make a reminder useful.

One core user need, several everyday contexts

I did not design separate roles for different kinds of users. Instead, I considered students and professionals tracking meetings, deadlines, or classes; parents and caregivers remembering appointments and school activities; and people who simply wanted daily reminders.

What connects those use cases is the need for speed, clear information, and minimal setup. That requirement shaped both the screen count and the way the event list presents information.

The screen plan

My original plan identified three essential destinations: login and account creation, a main view of upcoming events, and an add/edit screen. The main view needed to show each event’s title, date, and time, with a floating action button to create a new entry.

The event editor needed a title, date picker, time picker, and room for a short description. Saving or deleting would return the person to the main list. I wanted familiar Android interaction patterns, easily tappable buttons, high contrast, and predictable navigation.

The original data and architecture proposal

I initially proposed a local Room database with users and events tables, an MVVM structure, LiveData-driven updates, and Android background scheduling using AlarmManager or WorkManager. The intent was to separate storage, screen state, and reminder delivery so the interface could stay responsive.

That was the architecture proposal, not a claim that every library was used in the finished application. The Android code in this repository instead uses SQLiteOpenHelper for persistence, alongside separate event and reminder classes. The difference between a plan and an implementation is an important part of documenting the work accurately.
